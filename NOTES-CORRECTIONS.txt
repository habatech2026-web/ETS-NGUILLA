ETS N'GUILLA & FRERES — Notes de correction

Version de travail issue de l'archive originale.

Corrections apportées au code :
- Validation des quantités, des prix, des remises et des acomptes dans les deux parcours de vente.
- Refus d'une vente à crédit sans client sélectionné.
- Contrôle du stock disponible juste avant validation d'une vente standard ou POS.
- Enregistrement du coût d'achat dans les lignes de vente nouvelles pour stabiliser les marges historiques lorsque le prix d'achat du produit change ensuite.
- Amélioration du calcul de la marge du rapport : prise en compte du montant de vente après remise et déduction des retours traités.
- Affichage de la marge en pourcentage du prix de vente dans le tableau des marges (marge commerciale, et non taux de majoration du coût).
- Contrôle de la quantité retournable en cumulant les retours déjà enregistrés ; stockage de l'identifiant du produit sur les nouveaux retours.
- Blocage du traitement d'un retour déjà traité et recherche du produit par identifiant lors de la réintégration.
- Refus des sorties/pertes manuelles qui dépassent le stock disponible.
- Confirmation plus explicite avant suppression d'un mouvement, car cette suppression ne recalcule pas le stock.
- Une valeur de stock minimum égale à zéro est maintenant conservée lors de l'enregistrement d'un produit.
- Échappement de champs dynamiques dans le ticket POS.

Limites connues non résolues dans cette version :
- Le module d’inventaire permet maintenant un comptage physique et l’enregistrement local des écarts/ajustements. L’historique des sessions reste local au navigateur et n’est pas encore synchronisé dans une collection cloud dédiée.
- Les commandes fournisseurs ne possèdent toujours pas de lignes détaillées ni de réception stock intégrée.
- Les anciennes ventes ne possèdent pas de coût d'achat historique ; pour elles, le rapport utilise encore le coût d'achat actuel du produit comme solution de repli.
- Les règles de sécurité côté base de données, l'idempotence serveur, les conflits multi-utilisateurs et la synchronisation réelle doivent être vérifiés dans l'environnement connecté.
- Les calculs de retour déduisent le montant remboursé de la marge, mais un traitement comptable complet des retours (coût des marchandises retournées, avoirs, remboursements partiels) demande un modèle comptable dédié.

MISE À JOUR — CRÉATION DES COMPTES (écran Utilisateurs)
- Mode cloud : « Enregistrer » crée le vrai compte Firebase Auth (email + mot de passe, 6 caractères min.) via une 2e instance Firebase, sans déconnecter l'admin, puis enregistre le profil (rôle, uid) dans « utilisateurs ». Un rôle admin crée aussi admins/{uid}.
- Réservé aux administrateurs ; doublons d'email refusés ; messages d'erreur explicites.
- Prérequis : activer « E-mail/Mot de passe » dans Firebase Authentication et publier firestore.rules. Créer à la main dans la console le PREMIER document admins/{UID}.
- Mode local : comportement inchangé (profil local uniquement).

MISE À JOUR — GESTION DES UTILISATEURS DANS L'APP
- ✏️ Changer le rôle (met à jour admins/{uid}) ; 🔑 envoyer un lien de réinitialisation par email ; ⛔/✅ désactiver / réactiver (écrit disabled/{uid} : les règles Firestore coupent tout accès, et la connexion est refusée) ; « Mon mot de passe » pour changer le sien.
- Garde-fous : on ne peut ni se rétrograder, ni se désactiver, ni retirer le dernier admin actif.
- Limite technique : un navigateur ne peut pas supprimer un compte Firebase Auth ni fixer le mot de passe d'un autre utilisateur (réservé au SDK Admin / Cloud Functions). La désactivation + le lien de réinitialisation couvrent ces besoins.
- Les utilisateurs créés avant cette version n'ont pas d'UID : les recréer pour activer rôle/désactivation côté Firestore.
- firestore.rules à republier (ajout de la collection disabled).

MISE À JOUR — AMORÇAGE DU PREMIER ADMIN + ACCÈS PAR « MEMBRES »
- Plus de saisie manuelle dans Firestore : créez UN compte dans Firebase Authentication (email + mot de passe fort), publiez firestore.rules, puis connectez-vous à l'app. Si aucun admin n'existe, l'app propose « Devenir administrateur » ; elle crée atomiquement config/bootstrap, admins/{uid}, members/{uid} et votre profil (rôle admin). Opération possible une seule fois.
- Accès Firestore réservé aux comptes présents dans members/{uid} : une personne qui s'inscrirait via l'API Firebase sans être créée par un admin n'a aucun accès aux données. Désactiver un utilisateur retire son document members ; réactiver le recrée.
- Collection « disabled » abandonnée. Les comptes créés avec une version précédente n'ont pas de document members : les recréer depuis l'écran Utilisateurs.
- Ne désactivez PAS l'inscription publique de Firebase Auth : l'écran Utilisateurs en dépend pour créer les comptes. La protection vient du modèle « members » (un compte non listé n'accède à aucune donnée).
